The Strava source copes with Strava deactivating the install's API app. Strava deactivates a Standard Tier API app whose owner, the Strava account that registered it, has no active subscription, and then refuses every request made through it. The source used to read a refusal of an activity's zones or streams as that activity refused and mark it done, so a deactivated app could empty those backlogs with nothing fetched, and reactivating the app brought none of it back; the activity listing and the fetches of details and comments failed with an error that did not say why. A deactivated app now stops the source with the steps to fix it: subscribe on the owner's account, then reactivate the app on Strava's API settings page. Nothing is written while the app is deactivated, and once it is reactivated the source carries on where it stopped. The athletes connected through the app need no subscription. Activities already marked done this way are fetched again after a resync, from the Sources page or with `omnesis sources resync strava-activities`.

For an athlete without a Strava subscription, the source no longer asks Strava for each activity's heart-rate and power zones, which Strava refuses one read at a time; it asks once the athlete's profile shows a subscription. A profile that reports no subscription only in its older `premium` field counts as one without. An activity's zones that Strava serves without the time spent in each zone, or without saying whether they are heart-rate or power, no longer stop the source from fetching zones; what can be stored is stored and the activity is marked done. The setup wizard and the Strava entry of the sources documentation say that the app's owner needs a subscription, and that a new app connects one athlete and can be raised to ten.
